# Request identity and structured logging

## Scope

This contract covers API request identity, HTTP access logs, and NestJS system
logs. It is diagnostic telemetry, not an audit trail. Identity, authorization,
idempotency, business invariants, and event delivery must never depend on log
context.

The API emits newline-delimited JSON to standard output. The deployment
runtime, container platform, or future collector owns storage and shipping;
the application does not write log files or synchronously call a remote log
service.

## Request identity contract

Every request admitted by the NestJS middleware receives two response headers:

| Header | Ownership | Meaning |
| --- | --- | --- |
| `X-Request-Id` | Always generated by this API | Unique identity for this HTTP hop |
| `X-Correlation-Id` | Validated caller value or request-ID fallback | Lineage across a wider workflow |

The API always generates `X-Request-Id` as UUIDv4 and ignores an inbound value
with that name. This prevents an untrusted client from choosing the key used to
join the API's request logs.

An inbound `X-Correlation-Id` is accepted only when exactly one header value is
present and it is a canonical RFC-variant UUIDv4 or UUIDv7. Accepted values are
normalized to lowercase. Missing, repeated, comma-combined, malformed, or
oversized values are neither logged nor echoed; correlation falls back to the
new request ID and the business request continues.

Both identifiers are untrusted diagnostic labels. They do not grant access,
identify an actor or tenant, implement idempotency, select trace sampling, or
become database keys. Malformed HTTP rejected by Node.js before middleware is
outside this response-header guarantee.

For future outbound HTTP calls, a client adapter will propagate the correlation
ID and generate a new hop-local request ID. RabbitMQ messages will carry
correlation and causation explicitly in their envelope; consumers will create
a new processing identity. Ambient HTTP context will not cross an asynchronous
boundary.

## Log contract

Each record is one JSON object followed by one newline. The stable HTTP
completion schema is:

| Field | Meaning |
| --- | --- |
| `time` | ISO-8601 timestamp |
| `level` | `trace`, `debug`, `info`, `warn`, `error`, or `fatal` |
| `service` | `oms-api` |
| `deploymentEnvironment` | `local`, `test`, `showcase`, `staging`, or `production` |
| `event` | Stable machine-readable event name |
| `msg` | Static or framework-owned message |
| `component` | Optional application-owned component name |
| `requestId` | Server-owned HTTP-hop identity |
| `correlationId` | Validated workflow correlation identity |
| `http.method` | Allow-listed HTTP method or `OTHER` |
| `http.route` | Registered route template or a safe catch-all template |
| `http.statusCode` | Response status |
| `http.durationMs` | Rounded non-negative elapsed time |
| `err.type`, `err.code` | Optional sanitized classification without message, cause, or stack |

Route templates such as `/api/v1/orders/:orderId` are allowed. Raw URLs,
query strings, path parameter values, request or response bodies, arbitrary
headers, cookies, authorization values, and client IP addresses are not. A 404
may use NestJS's registered low-cardinality catch-all template; it never uses
the requested path.

The adapter recursively redacts sensitive structured keys case-insensitively,
including compound password, token, secret, API-key, private-key, card, and
cookie fields. Redaction is defense in depth, not permission to log arbitrary
DTOs, entities, configuration, environment maps, or provider responses. Error
and fatal calls always use fixed messages and allow-listed fields; raw error
messages, stacks, causes, and detail objects are discarded. Structured values
also have depth, field-count, array-length, and string-length bounds.

`requestId`, `correlationId`, `service`, `deploymentEnvironment`, `time`, and
`level` are reserved. A per-record payload cannot replace them.

Non-error Pino messages are not content-inspected because arbitrary string
scrubbing cannot reliably identify secrets. Today, only NestJS lifecycle
messages and adapter-owned static HTTP messages can reach that path. Business
feature paths are forbidden from importing NestJS or Pino loggers. Their future
application-owned logging port will accept stable events and structured
allow-listed fields rather than user-derived message strings.

## Vendor boundary

`nestjs-pino`, Pino, and Pino HTTP are API platform adapters. Domain code must
not import them, read async-local context, or contain diagnostic logging calls.
Feature modules must not inject `PinoLogger`, create Pino children, or call
`PinoLogger.assign`; child bindings bypass per-record sanitation. Before the
first business feature needs diagnostic events, the platform will expose a
small application-owned logger that accepts stable event names and allow-listed
fields. Repository lint rules already prohibit vendor imports from business
module and API feature paths; the typed port will strengthen that boundary.

The current adapter uses the async-local store already maintained by
`nestjs-pino`. This gives request-scoped bindings without constructing a NestJS
request-scoped dependency graph. The context is diagnostic only and is tested
under concurrent awaited work.

## Levels and health policy

| Outcome | Level |
| --- | --- |
| Normal response, including expected 4xx | `info` |
| Rate limited (`429`) or aborted request | `warn` |
| Failed readiness (`503`) | `warn` |
| Other 5xx | `error` |
| Successful liveness or readiness | No access record |

Successful health polls still receive identity headers. Suppressing their
access records avoids high-volume noise. A failed readiness poll remains
visible until dependency metrics and rate-limited state-transition events are
implemented. Terminus's own logger remains disabled so dependency exceptions
cannot create a second, unsanitized record.

`LOG_LEVEL` is validated at startup. It defaults to `debug` in development,
`silent` in test, and `info` in production. A production Node.js runtime must
set `DEPLOYMENT_ENVIRONMENT` explicitly so a public showcase is labelled
`showcase` rather than being presented as production.

Configuration, dependency-injection, and socket-bind failures are caught at
the composition root. A partially created application is closed, one fixed
fatal JSON record is written synchronously to standard error, and the process
receives a non-zero exit code. The original exception is intentionally absent
from that emergency record.

## Why this design

- Pino provides low-overhead structured output and a mature HTTP lifecycle;
  `nestjs-pino` integrates it with NestJS system logging and asynchronous
  request context.
- Server-owned request IDs prevent spoofed log joins while a separately
  validated correlation ID preserves caller workflow lineage.
- An allow-list-first HTTP serializer prevents common credentials and personal
  data from reaching output at all; redaction handles accidental structured
  fields as a second barrier.
- Standard output works with local Docker, free showcase providers, Kubernetes,
  and future collectors without coupling application availability to a log
  backend.

## Alternatives considered

- **NestJS JSON `ConsoleLogger`:** fewer dependencies, but weaker HTTP lifecycle
  events and no built-in request-bound child context.
- **Winston:** useful when an application owns many transports, but transport
  richness is unnecessary when containers own log shipping.
- **Custom Pino middleware and `AsyncLocalStorage`:** maximum control, with more
  lifecycle, abort, and context-cleanup code to maintain and test.
- **Request-scoped NestJS providers:** conceptually direct, but add a dependency
  graph per request and still require separate HTTP completion handling.
- **OpenTelemetry and W3C `traceparent` now:** the correct future tracing
  direction, but premature before a trace provider, propagation policy, and
  sampling budget exist. Correlation ID remains a separate business-workflow
  label.
- **Trust inbound request IDs:** rejected because clients could create
  collisions, misleading joins, and high-cardinality abuse.

## Trade-offs

- JSON is less readable in a local terminal; developers may pipe output through
  an external formatter without changing application output.
- Omitting bodies, raw URLs, and exception text reduces immediate debugging
  detail. Stable codes, identifiers, metrics, and later scrubbed traces must
  provide diagnosis safely.
- Async-local context has runtime overhead and does not cover detached work. It
  remains diagnostic and explicit message envelopes cover asynchronous flows.
- Strict UUID correlation values reject other useful formats. This bounds
  cardinality and complexity now; W3C trace identifiers will have their own
  validated contract later.
- Repeated readiness warnings can be noisy during a long outage. Metrics and
  rate-limited dependency state changes will replace per-poll warnings.

## Interview questions

1. **What is the difference between a request ID and correlation ID?** A request
   ID identifies one processing hop; a correlation ID links work across a wider
   workflow.
2. **Why ignore an inbound request ID?** It prevents clients from controlling
   the API's authoritative log-join key. Validated caller lineage belongs in a
   different field.
3. **Why use async-local storage instead of request-scoped providers?** It
   propagates diagnostic bindings across awaited work with less dependency
   injection overhead, but it must never carry business correctness.
4. **Why are logs not audit records?** Logs are sampled, retained, and shipped
   operationally; audits require durable, access-controlled, business-defined
   evidence.
5. **Why not log bodies and redact later?** Unbounded objects create PII,
   credential, PCI, cost, and cardinality risk. Preventing collection is safer
   than attempting exhaustive cleanup.
6. **How will correlation cross RabbitMQ?** An explicit message envelope carries
   correlation and causation; each consumer creates its own processing ID and
   remains idempotent.

## Future improvements

- Add the application-owned typed logger and extend the existing vendor-import
  boundary before business feature logging begins.
- Add RFC 9457 Problem Details with safe error codes and both response IDs.
- Add OpenTelemetry trace/span identifiers and validated W3C propagation.
- Add worker and RabbitMQ message context with explicit correlation and
  causation envelopes.
- Add metrics, SLOs, rate-limited dependency state transitions, and alerts.
- Add trusted-ingress proxy configuration before using forwarded client data.
- Expose identity headers through a deliberate CORS policy when the browser
  frontend is introduced.
- Load-test asynchronous standard-output buffering and define explicit logger
  flushing during shutdown.
